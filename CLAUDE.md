# CLAUDE.md

Sandboxes is a macOS app for managing [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/). It's a front end for the `sbx` CLI: every action runs an `sbx` command and parses its output.

## Targets and build

- macOS 26 or later only. Use macOS 26 APIs, including Liquid Glass, freely, with no `#available` checks or fallbacks for older systems.
- Swift 5 language mode (`SWIFT_VERSION: "5.0"`), SwiftUI first, AppKit where SwiftUI can't do it (windows, activation policy, `NSWorkspace`).
- No App Sandbox and no hardened runtime, because the app launches `sbx`, `brew` and terminals. Builds are ad-hoc signed (`CODE_SIGN_IDENTITY: "-"`) and not notarized.
- `project.yml` is the source of truth. `Sandboxes.xcodeproj` and `Support/Info.plist` are generated by XcodeGen and git-ignored, so never edit them. Add Info.plist keys and build settings in `project.yml`.
- The only third-party dependency is [Sparkle](https://sparkle-project.org), which installs updates (`UpdateChecker`). Don't add others unless asked.
- There are no tests or SwiftUI previews yet.

### Building from a Linux sandbox

The app can't be compiled on Linux: SwiftUI, AppKit, UserNotifications and ServiceManagement only exist in Xcode's macOS SDK, and the icon needs Xcode's `actool`. The only compile check is CI (`.github/workflows/build.yml`, on `macos-26`), which runs on every push to a PR. After pushing, read the result:

```bash
gh run list --branch "$(git branch --show-current)" --limit 1
gh run view <run-id> --log-failed
```

Because nothing compiles locally, be strict with APIs: confirm any API you aren't sure of in Apple's docs (see below) rather than guessing, and say in your summary that the change hasn't been built until CI passes.

## Layout

- `Sources/Sandboxes/SandboxesApp.swift`: the `App`, its scenes (the main `Window`, the **New Sandbox** `Window`, `MenuBarExtra`, `Settings`) and `AppDelegate`, which owns the long-lived stores.
- `Models/`: `@Observable` stores and value types, plus parsers for `sbx` output.
- `Services/`: talking to the outside world: `SbxCLI` (runs processes), `ShellEnvironment` (login shell `PATH`), `TerminalLauncher`, `ClaudeDesktopLauncher`, `ApprovalNotifier`, `UpdateChecker`, `AppWindows`, `Homebrew`.
- `Views/`: SwiftUI views, one file per window, screen or sheet.
- `Design/AppIcon.icon`: Icon Composer file. Its layers come from `scripts/generate-app-icon.py`, which also writes `Design/AppIcon.svg` and `Design/AppIconArtwork.svg` (the artwork without the background, for the website, where the robot peeks out of the sand on load).
- `site/`: the website on GitHub Pages (`index.html`, `style.css`) and `install.sh`, published by `.github/workflows/pages.yml`, which copies in `Design/AppIcon.svg` and `Design/AppIconArtwork.svg`. `scripts/preview-site.sh` serves it locally with the same files.

## Patterns to follow

### State

- Stores are `@MainActor @Observable final class`es (`SandboxStore`, `SbxStatus`, `UpdateChecker`, `RecentsStore`). `AppDelegate` creates the ones that must outlive the window, and the scenes pass them down with `.environment(_:)`. Views read them with `@Environment(SandboxStore.self)`.
- Expose state as `private(set) var` and change it through methods on the store. Mark bookkeeping that views don't need with `@ObservationIgnored`.
- Persist preferences in `UserDefaults`, with the key in a `static let …Key` constant next to the code that owns it. Views use `@AppStorage` with the same key.
- Long-running loops are `async` methods (`refreshPeriodically()`, `checkPeriodically()`) started as a `Task` from `AppDelegate`, and they stop when the task is cancelled.

### Running `sbx`

- All processes go through `SbxCLI`: `run` (collect output), `runChecked` (throw `SbxError` on a non-zero exit) or `stream` (output as it arrives; cancelling the task terminates the process). It uses `ShellEnvironment.environment` so a GUI launch sees the login shell's `PATH`. Don't create `Process` directly elsewhere (the only other one reads the login shell's environment in `ShellEnvironment`).
- Interactive commands (`sbx exec -it`, `sbx run`) open in the user's default terminal through `TerminalLauncher`, not in the app.
- Store actions report failures by setting `actionError` with a title like `Couldn't Stop “name”` and the error's `localizedDescription`, rather than throwing to the view.
  The exception is saving from a sheet that edits something, such as the secret editor's `SecretStore.save(_:)`: it throws, so the sheet stays open with what was entered and shows the error next to it.
- Destructive or security-relevant actions (remove, approve, deny) confirm first with `confirmationDialog`.

### Parsing `sbx` output

`sbx`'s JSON isn't documented and changes between versions. Parsers (`SandboxListParser`, the network and approval parsers) use `JSONSerialization` and accept several shapes and key spellings rather than a strict `Decodable` model. They skip any warnings printed before the JSON, and some fall back to the table output when `--json` isn't supported. Keep new parsing just as tolerant.

Don't guess `sbx` flags or subcommands. Check them with `sbx <command> --help` when `sbx` is installed, or else in the [`sbx` CLI reference](https://docs.docker.com/reference/cli/sbx/) (see [Looking up `sbx` docs](#looking-up-sbx-docs)). Neither describes what `--json` output contains, so for output fields go by the existing parsers or ask for real output.

### Concurrency

- UI types and stores are `@MainActor`. Mark static constants and pure helpers that other contexts need `nonisolated`.
- Callbacks from `Process` and pipes arrive on background queues. Hop back with `DispatchQueue.main.async { MainActor.assumeIsolated { … } }`, as `SbxCommandRun` and `AppWindows` do.
- Small thread-safe helpers are `final class … : @unchecked Sendable` guarded by an `NSLock`.

### UI

- Use system Liquid Glass styles: `.buttonStyle(.glassProminent)` for primary actions, `.glassEffect(.regular, in: …)` (`.regular.interactive()` for tappable shapes) for floating chrome. Don't fake glass with materials or custom blurs.
- The app keeps running in the menu bar when its windows close, and leaves the Dock when none is visible or minimized. Open windows through `AppWindows` (`showMain()`, `showCreate()`, `showSettings(_:)`), which also switch the activation policy, not `openWindow` directly. To open New Sandbox, call `store.presentCreate(workload:)`.
- Each `Window` scene has an ID in `AppWindows`, an `AppWindows.open…` closure that `ContentView` and `MenuBarLabel` set from `openWindow` (the menu bar label is always there, so it works with every window closed), and a `WindowReader(kind:)` in its content so `AppWindows` can track it (Settings has one too, and opens with `openSettings`). Close one with `dismissWindow(id:)`.
- Use a separate `Window` rather than a sheet when the content needs a title bar, such as New Sandbox's sidebar of sections (`NavigationSplitView`). Call it the **New Sandbox window** in code comments and text, not "the create sheet".
- Write UI text in Apple's style: title case for buttons, menus and alert titles, curly quotes around names (`“name”`), `…` on items that open something needing more input, sentence case for chips and badges (“Restart needed”), and plain sentences for messages.

### Code style

- Comments explain why, or describe what the user sees. Doc comments (`///`) go on types and non-obvious members. Match the existing density and don't add comments that restate the code.
- Use British spelling in prose, comments and docs (labelled, centre), following the existing README.
- Prefer `enum` namespaces with static members for stateless services (`SbxCLI`, `Homebrew`, `AppInfo`).

- `README.md` › **Features**: anything a user can now do or see.
- `README.md` › **Commands the app runs**: every `sbx` (or `brew`) command the app runs, with its exact arguments. Add, change or remove rows whenever `SbxCLI` calls change.
- `README.md` › **Update checks**, **Test builds**, **Releases**: when `UpdateChecker`, the CI workflow or the versioning changes.
- `README.md` › **Requirements**: the macOS version, and the minimum `sbx` or Claude Desktop version a feature needs.
- `project.yml` comments, and the comments in `.github/workflows/build.yml`, when build settings or versioning change.
- `site/index.html`: its feature rows (Sandboxes, Access, Configuration) summarise the main items in the README's **Features**, and its requirements repeat **Requirements**. Update the site when a feature belongs in one of those rows or a requirement changes. `.github/workflows/pages.yml` fills in the release button (`<a id="release" … href="…">`) when it deploys, so keep its `id` and `href`.

## Looking up Apple docs

Much of the macOS 26 API (Liquid Glass, new SwiftUI scene and toolbar APIs) is newer than most training data, so look it up instead of relying on memory.

- `developer.apple.com/documentation/...` pages are rendered with JavaScript, so fetching them returns almost nothing. Fetch the JSON behind them by inserting `/tutorials/data` and adding `.json`:

  ```bash
  curl -s 'https://developer.apple.com/tutorials/data/documentation/swiftui/view/glasseffect(_:in:).json'
  ```

  The path is the page's path, lowercased. `metadata.platforms` gives the OS versions a symbol was introduced in (check it's available on macOS, and not iOS only), `abstract` gives the summary, `primaryContentSections` gives the declaration and discussion, and `topicSections` and `references` list related symbols.
- To find a symbol, start from a framework or type page such as `.../documentation/swiftui/view.json` and follow `topicSections`.

## Looking up `sbx` docs

### `sbx --help` (first choice)

Check `command -v sbx`. When it's installed (for example by an sbx CLI kit), its help is the most reliable source for the version installed:

- `sbx <command> --help` works for every command without signing in. Most work without the daemon too. The exception is the `sbx kit builder history` commands, which need it even for `--help`: start it with `sbx daemon start --detach`, and stop it with `sbx daemon stop` when you're done.
- Some commands are hidden from their parent's help but have help of their own. `sbx policy approval` (`ls`, `inspect`, `respond`) isn't listed in `sbx policy --help` or on the docs site, but `sbx policy approval --help` works.
- `sbx policy approval ls` has no `--json` flag (as of v0.48.0), so the app's fallback to table output is the path in use. `sbx policy approval respond` takes `APPROVAL-ID --option OPTION-ID`.
- `sbx version` gives the installed version. Behaviour differs between releases, so say which version you checked.
- Commands that read real state (`ls`, `policy ls`, `policy log`, `policy approval ls`, `template ls`, `mcp ls`) fail with "not signed in to Docker". Don't run `sbx login`; ask the user for real output instead. Local sandboxes can't run inside a sandbox anyway, since there's no KVM.

### CLI reference

- `https://docs.docker.com/reference/cli/sbx/<command>/<subcommand>/`, for example `.../sbx/policy/log/`. Pages have usage, description, options, global options and examples. The sidebar on any page links to all of them.
- **Fetch reference pages as HTML.** Their `.md` versions are empty apart from the title. This prints the page's text:

  ```bash
  curl -s https://docs.docker.com/reference/cli/sbx/policy/log/ | python3 -c 'import html,re,sys; t=sys.stdin.read(); t=t[t.find("<article"):t.find("</article>")]; t=re.sub(r"<(script|style)\b.*?</\1>","",t,flags=re.S); print(re.sub(r"[ \t]*\n\s*","\n",html.unescape(re.sub(r"<[^>]+>"," ",t))).strip())'
  ```

- **Not complete.** It has no pages for `sbx policy approval` or `sbx policy profile`, though both exist. Don't take a missing page to mean a command doesn't exist.
- **No output schemas.** Neither the reference nor `--help` describes the fields `--json` or `--format json|yaml` produce, so they can't settle what a parser should expect. Don't change how the app calls or parses a command without real `sbx` output to go on.

### Guides

`https://docs.docker.com/ai/sandboxes/...` pages are served as Markdown: add `.md` to the page path, for example `https://docs.docker.com/ai/sandboxes.md`. `https://docs.docker.com/llms.txt` lists the guide pages.

## Git and PRs

- Commit and PR titles are short imperatives describing what the user gets, such as "Show when a newer release is available". PRs are squash-merged, with the PR number in the title.
- CI builds a DMG for every PR. Mention in the PR description what to check in that build.
